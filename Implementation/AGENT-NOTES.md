## Git workflow
- `main` is the integration branch. Parallel agents work in **git worktrees** on task branches `p<phase>-<task>-<slug>`. Agents do **not** merge to `main`; report `BRANCH: <name> @ <commit>` and the orchestrator merges.
- Conventional Commits; every commit ends with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.
- `.gitattributes` stores LF, checks out CRLF. `.editorconfig` demands CRLF; run `dotnet format` before committing or `dotnet format --verify-no-changes` fails with ENDOFLINE.
- Run plain `dotnet format` (never `dotnet format --no-restore`): without restore it compiles against unresolved references and silently strips `using` directives from unrelated files.
- Migrations: append-only, named `Phase<N>_<Task>_<What>`. Never edit another task's migration.
- After any `git merge main`, run `grep -rn -E "^(<<<<<<<|=======|>>>>>>>)" Implementation src tests README.md` and fix every hit BEFORE `git add -A`; two merges have shipped conflict markers into STATUS.md/DECISIONS.md already. Keep both sides in the append-only docs.
- `src/NcaafPickEm.Infrastructure/Data/Migrations/.editorconfig` marks that folder as generated code. Without it `dotnet ef migrations add` fails the next build on IDE0161/IDE0005. Do not hand-write code there and do not reformat what EF emits.

## Jobs (from P0-06)
- Everything scheduled lives in `src/NcaafPickEm.Infrastructure/Jobs/`. One `BackgroundService` (`JobScheduler`) calls `SchedulerTick.TickAsync(nowUtc, ct)` every minute; `TickAsync` holds all the logic so tests never wait on the wall clock. `Jobs__Enabled=false` makes the hosted service log one line and return (`ApiFactory` already sets it).
- **Add a cron job**: implement `IScheduledJob` (`Name`, `CronExpression`, `RunAsync(scheduledFor, ct)`) in `Infrastructure/Jobs/`, then one `services.AddScheduledJob<YourJob>();` line in `Infrastructure/DependencyInjection.cs`. Jobs are scoped, so `AppDbContext` is fine to inject. Cron is a standard **five-field** expression evaluated in **Eastern** (`SeasonCalendar.Eastern`) by Cronos — write `30 23 * * *` for 11:30 PM ET and let the scheduler do the DST maths.
- **Add a one-shot** (a due time that lives in the database, like the week lock or the Saturday reminder): implement `IOneShotJob` — `Name`, `GetDueAsync(nowUtc, ct)` returning `OneShotOccurrence(Key, DueUtc)`, and `RunAsync(occurrence, ct)` — then `services.AddOneShotJob<YourJob>();`. This is the card's `IOneShotScheduler` (D-034). Answer the naive query and stay stateless: the tick drops occurrences dated after `nowUtc` and skips ones already recorded.
- Idempotency is the `JobRuns(JobName, ScheduledForUtc)` unique index. The tick inserts the row **before** running and treats a duplicate key as "someone else has this one". A one-shot's row is `JobName = "{Name}:{Key}"`, so name + `:` + key must fit 60 characters. **Write every job to be safely re-runnable** (D-033): a crash between claim and finish, or the catch-up window, can offer the same occurrence again.
- Catch-up is bounded to `Jobs__CatchUpMinutes` (60). A job that has never run starts its window 60 minutes back, so a fresh database logs up to twelve heartbeats on first boot.
- **Testing**: build a container over the test database with `SchedulerHarness.Create(fixture, services => services.AddScoped<IScheduledJob>(_ => job))` and drive `harness.Tick.TickAsync(anyInstant, ct)`. `SchedulerHarness.CronForMinuteOf(instant)` pins a cron to one Eastern minute, `UniqueJobName(prefix)` keeps the shared database's `JobRuns` table collision-free, `ReadRunsAsync(name)` reads the rows back. `RecordingScheduledJob` / `RecordingOneShotJob` count invocations. See `JobSchedulerTests` and `OneShotTests`.
- `HeartbeatJob` (`*/5 * * * *`) is proof of life and owns no table. `GET /api/admin/data-status` shows the last 50 runs; scope an admin route with `RequireAnyLeagueCommissioner()` (403, not 404, for a non-commissioner — D-035).
- **Refresh jobs** (P2-04, `Infrastructure/Jobs/Refresh/`): `TeamsRefreshJob` (Tue 03:00 ET), `ScheduleRefreshJob`/`ScheduleRefreshDailyJob` (Tue 03:10 ET, then daily 04:00 ET Wed-Sat — both delegate to `ScheduleRefreshRunner`, which folds the calendar refresh in ahead of the schedule per D-057/D-078), `RankingsRefreshEveningJob`/`RankingsRefreshTuesdayJob` (Sun+Mon 20:00 ET via one Cronos day-of-week list, then Tue 03:20 ET — both delegate to `RankingsRefreshRunner`), `LinesRefreshJob` (daily 23:30 ET). Each resolves "the season" via `RefreshJobSupport.CurrentSeasonYear(nowUtc)` (D-077: no global current-season config exists yet) and "the week" via `ISeasonWeekSource` + `SeasonCalendar.CurrentWeekAt`; schedule refresh also does the following week when it is still regular season. None throw on a failed ingest — `ReferenceDataIngestService` already recorded `DataRefreshStatus` (D-056/D-057), so a job logs a warning and returns. `ReferenceDataIngestService` (P2-02) is registered unconditionally, not only for `Providers:ReferenceData=Cfbd` (D-081), so the jobs work in Fixture mode too.
- **`SaturdayPoller`** (`Infrastructure/Jobs/SaturdayPoller.cs`, a `BackgroundService`, gated on `Jobs:Enabled`): re-evaluates every minute via `SaturdayPollerSchedule.Evaluate(nowUtc, activeSets, activeSource)` — a pure class (04-Domain-Algorithms.md section 10) taking flattened `PollerWeekSet(LeagueId, LockAtUtc, AllGamesTerminal)` rows and returning `PollerDecision(InWindow, NextPollAtUtc, Cadence)`. Window opens at `min(LockAtUtc) - 5 min` over sets with a still-playing active game and closes when every such set's games are all terminal (Final/Voided/Postponed/Cancelled) or at 03:00 ET the following Sunday, whichever first; cadence is 5 min for Espn/Fixture, 10 for Cfbd (whatever `ILiveScoreHealth.ActiveSource` is right now). `SaturdayPoller.EvaluateOnceAsync` builds the active sets from `WeekGameSetGames` (grouped by league, joined to `Games.Status`), calls `ResetForNewDay()` once per window, and delegates to the static `SaturdayPoller.PollOnceAsync(services, database, timeProvider, easternDate, logger, ct)`. **The loop re-evaluates every minute but only calls the provider on the cadence** — the tick is not the poll. **Everything about the window is keyed on the window's Saturday, never on "today"** (D-090): `PollerDecision.SaturdayEastern` is the date handed to the provider (ESPN buckets the post-midnight final on the Saturday it kicked off), it is what `ResetForNewDay()` is keyed on so a midnight tick cannot clear a fallback that must hold all game day, and `GameDayInstant` resolves the *week* at Saturday evening while the Eastern clock reads Sunday before 03:00, because the season calendar has already rolled over by then. A poll that throws is recorded on `DataRefreshStatus(Scores)` and swallowed by the loop's guard, like `JobScheduler`'s tick — the `BackgroundService` must never die on a provider outage — `ILiveScoreProvider.GetScoresAsync` then `LiveScoreApplyService.ApplyAsync`, returning the `LiveScoreApplyResult` so a test can assert on it without subscribing. `POST /api/admin/refresh/Scores` and the manual "refresh now" admin action call `ILiveScoreProvider`/`LiveScoreApplyService` directly for today's Eastern date, bypassing the window (the card's "regardless of window").

## Push (from P7-01)

- **Sending a notification is one call**: inject `Infrastructure/Push/NotificationService` (scoped) and `await notifications.SendToUserAsync(userId, NotificationType.X, leagueId, week, new PushPayload(title, body, url, tag), ttl: null, ct)`. It fans out to every device the user has subscribed, writes the `NotificationLog` row, deletes dead subscriptions and queues retries. P7-03's jobs and event handlers should call nothing else.
- **`SendToUserAsync` writes the log row before it sends**, and a duplicate-key violation on the filtered unique index is the once-per-week check: it returns `Skipped` and sends nothing. So a reminder job does *not* need its own "did I already send this?" query — just call it (D-071). Event types (`GamesAdded`, `GameRemoved`) are not covered by the index and can repeat.
- **One row per notification, not per device** (D-071). `Result` is the best outcome across the member's devices: Sent > Failed > Expired > Skipped. A `Failed` row whose `Error` says "Retry N of 3 is due at ..." still has attempts outstanding and becomes `Sent` if one works.
- **TTL** comes from `PushTtl.For(type)` — 1 hour for the three reminders, 4 hours for the two event types (D-072). Pass `ttl:` only to override.
- **Retries** are rows in `PushRetries` drained by `PushRetryJob : IOneShotJob` (+1, +5, +15 minutes, then `Failed`). Nothing to wire up: `AddPush` registers the job.
- **Transport** is `IPushSender`. `WebPushSender` (WebPush 1.0.13) when `Push__VapidPublicKey`/`PrivateKey`/`Subject` validate, otherwise `NullPushSender`, which logs a warning and reports `Failed` — **the app boots with no keys**, and `GET /api/push/vapid-public-key` answers 503 (D-073). Generate a pair with `deploy/generate-vapid.ps1` (wraps `dotnet run --project src/NcaafPickEm.Api -- generate-vapid`; do not add `--verbosity`/`--nologo` to that line or the SDK eats the argument).
- **Testing a notification**: `tests/NcaafPickEm.Api.Tests/Infrastructure/FakePushSender` is scriptable per endpoint (`Script(endpoint, PushSendResult.Gone(...), PushSendResult.Accepted())` — the last outcome repeats) and records every payload and TTL. Register it with the new `ApiFactory(connectionString, configureServices: services => { services.RemoveAll<IPushSender>(); services.AddSingleton<IPushSender>(fake); })` hook; `TryAdd` will not win against the app's own registration. `PushDeliveryTests` is the worked example, including how to drive `PushRetryJob` directly (`GetDueAsync` takes the instant, so no clock fiddling is needed).
- **Looking a device up**: always `PushEndpointHash.Compute(endpoint)` and compare against `EndpointHash`; the unique index is on the hash, not on `Endpoint` (D-017, D-074). Deleting a subscription goes through `PushDelivery.RemoveSubscriptionsAsync`, which nulls the `NotificationLog.SubscriptionId` rows that point at it first (every FK is `Restrict`).
- **Development test push**: `POST /api/push/test` (Development/Testing only, commissioner of any league) sends "Test notification" to the caller's own devices, logged as `GamesAdded` in week 0 so it can never burn a real reminder.
- **A job with real DI dependencies, tested without `SchedulerHarness`** (P3-04's `RegenerateGameSetsJob`/`EnsureCurrentWeekSetsJob`, which need `GameSetService` and everything it drags in): `SchedulerHarness`'s bare `ServiceCollection` only wires `AppDbContext` + the scheduler itself, so a job with real application-service dependencies is easier to drive straight off the real app container — `ActivatorUtilities.CreateInstance<TJob>(scope.ServiceProvider)` inside a scope from `factory.Services` (`ApiFactory`/`ApiTestFixture.PinnedFactory`), then call `job.RunAsync(scheduledFor, ct)` directly. Skips cron-string matching (covered separately by `JobSchedulerTests` for the scheduler itself) but exercises the job's actual logic against real data.

### Reminder jobs and event notifications (P7-03)

- **`Infrastructure/Notifications/`**: `NotificationMessages` is the one place with the Feature 11 catalog text — a static method per catalog entry returning a `PushPayload` (`Title` a short label, `Body` the catalog sentence verbatim with placeholders filled, `Url` = `PicksUrl(leagueId, week)` or `LeagueHomeUrl(leagueId)`, `Tag` a per-type/league/week collapse key, D-091). `ReminderRecipients` is the shared query layer: `CurrentUnlockedSetsAsync` (which league/week is "current" right now, skipping no-set/locked/no-active-games leagues, D-092), `UnsubmittedMembersAsync` (active members whose `WeekSubmissions.Status != Submitted`, no row = `NotStarted`), `PicksLeftAsync` (active games minus the member's picks on them). All three re-query at call time — nothing about a job's recipients is computed ahead of it actually running.
- **`FridayMemberReminderJob`/`FridayCommissionerSummaryJob : IScheduledJob`** (`0 20 * * 5` / `0 21 * * 5`, Eastern). The commissioner summary skips a league entirely when nobody is unsubmitted; otherwise every active commissioner gets one message naming everyone unsubmitted via `MemberNameProjection`'s rule (inlined in the `ReminderRecipients` query, not called by name since it joins across a subquery).
- **`SaturdayReminderOneShot : IOneShotJob`**: due time is `WeekGameSets.LockAtUtc - 1h`, re-read from the database on every `GetDueAsync` call with `Key = WeekGameSetId`, so a commissioner moving the lock time produces a new `(Name:Key, ScheduledForUtc)` pair the scheduler treats as a fresh occurrence (D-034) — see D-094 for why the query is unbounded rather than windowed like `PushRetryJob`'s. `RunAsync` re-checks `LockedUtc`/`LockAtUtc` defensively even though `GetDueAsync` already filters them out, since an occurrence claimed before a race can still reach `RunAsync`.
- **`GamesAddedNotificationHandler`/`GameRemovedNotificationHandler : IDomainEventHandler<...>`**: `GameAddedToSet` already carries every added row's id for one regeneration or manual add (P3-03's event shape), so "coalesce N adds into one message" needed no event change — just `domainEvent.GameSetGameIds.Count`. Recipients for GamesAdded are "was Submitted at the moment of the add", computed as `Status == Submitted OR (SubmittedUtc != null AND SubmittedUtc < OccurredUtc)` so the answer does not depend on whether P4-04's own handler on the same event ran first or second (D-093, D-046's "registration order" note). GameRemoved recipients are every member with a `Picks` row on the removed `WeekGameSetGameId`, regardless of submission status. Both skip entirely when `WeekGameSets.LockedUtc != null` (defensive; a locked week's own generation/removal is already a no-op upstream).
- **Testing without going through `SchedulerHarness`**: `ReminderJobTests`/`SaturdayOneShotTests` mostly seed `WeekGameSets`/`WeekGameSetGames`/`WeekSubmissions` rows directly via `ExecuteDbAsync` rather than `GameSetService`/`PickService`, since these jobs only read that state — direct seeding gives exact control over `LockAtUtc` and status without pulling in rule/point-value machinery. `SaturdayOneShotTests` seeds its own throwaway leagues with `LockAtUtc` relative to `DateTimeOffset.UtcNow` (not the Week 7, 2026 fixture calendar, which sits a month in the future relative to when tests actually run) so a real `SchedulerHarness.Tick` at `DateTimeOffset.UtcNow` sees them as due/not-due deterministically. `EventNotificationTests` goes the other way — through the real `GameSetService` HTTP endpoints (`gameset/generate`, `gameset/games/{gameId}`) — so the real `DomainEventCollector`/`IDomainEventDispatcher` fires these handlers exactly as production does, rather than raising events by hand. All three swap `IPushSender` for `FakePushSender` the same way `PushDeliveryTests` does.
- **Who is a recipient, in one sentence (P7-03 review, D-113..D-115)**: every recipient query in `Infrastructure/Notifications` filters `Memberships.RemovedUtc == null` — including `GameRemovedNotificationHandler`'s join, because a removed membership keeps its `Picks` rows as locked-week history (04 section 6) and "has a pick row" is not "is in the league". `SaturdayReminderOneShot.RunAsync` sends nothing once `LockAtUtc` has passed, not just once `LockedUtc` is set: the scheduler only drops *future* occurrences, so a late host hands over a stale one and `LockWeekJob` may not have locked the week yet. Both Friday jobs wrap their per-league body in a `try`/`catch` (clear the change tracker, log, count, continue) because `SchedulerTick` claims a cron occurrence before running it and never replays it — an escaping exception would silently cost every league later in the loop its reminder for that week.

### Client push flow (from P7-02)
- `wwwroot/js/push.js` (ES module, no inline `<script>` per 05-Conventions.md) is the only place that touches the browser's Push API: `getSupport()` (`{ supported, isIos, isStandalone, permission }` — `supported` is false on iOS until `isStandalone`, since a Safari tab cannot receive push at all), `subscribe(vapidPublicKey)` (calls `Notification.requestPermission()` then `PushManager.subscribe`; must be invoked from a tap handler — the browser silently refuses the permission prompt otherwise), `getExistingSubscription()`, `unsubscribe()`. Every returned object uses explicit camelCase keys matched on the C# side by `[JsonPropertyName]` (`Web/Services/PushInterop.cs`: `PushSupportInfo`, `PushSubscribeResult`, `PushSubscriptionInfo`) rather than relying on Blazor's default interop JSON convention.
- `Web/Services/IPushApi`/`PushApi` (+ `Fakes/FakePushApi`, same `DEBUG && USE_FAKE_API` switch as every other client, D-043/D-044) wraps `/api/push/*`. `GetVapidPublicKeyAsync` returns `null` for the 503 "not configured" response instead of throwing — that is a state `NotificationSettings` renders, not a failure.
- `Components/NotificationSettings.razor` (replaces P1-03's `NotificationsSettingsPlaceholder`) is the state machine: unsupported browser -> iOS-not-installed (Home Screen instructions) -> server unavailable (503 key) -> permission denied -> off -> "off on this device" (browser has a subscription, `GET /api/push/status?endpoint=` says the server does not — re-posts the *existing* browser subscription rather than re-requesting permission) -> on (Turn off, plus a `#if DEBUG` "Send test notification" button gated additionally on `IsCommissioner`, D-107). A `?simulate=ios|off|on|unavailable` query flag (`#if DEBUG` only, D-106) forces a state without touching the real Push API, for screenshots and for environments where headless support is uncertain.
- Both service workers' `push` handler does `event.data.json()` -> `showNotification(title, { body, tag, icon: 'icon-192.png', badge: 'badge-96.png', renotify: true, data: { url } })`; `notificationclick` closes the notification, resolves `url` against `self.registration.scope`, and focuses+navigates an existing window (falls back to `clients.openWindow`) so an installed iOS app reuses its one standalone window instead of opening a second. `service-worker.js` (dev) and `service-worker.published.js` carry byte-identical copies of these two handlers — kept in sync by hand, there is no shared module between them.

## Leagues (from P1-01)
- `Domain/Leagues/LeagueRules` is the pure invariant layer: `ValidateName`, `ValidateWeekRange` (against `IReadOnlyList<SeasonWeek>`), `EnsureRoomForNewMember` (cap 50), `EnsureNotActingOnSelf`, `EnsureAtLeastOneCommissionerRemains`, `ApplyTransfer` (mutates the two `Membership` objects it is given; never touches a third), `ValidateDisplayNameOverride`. Every check throws `LeagueRuleViolation` (a `Code` + message); `Api/Endpoints/LeagueRuleViolationResults.ToProblem()` maps the code to 400 or 409 `ProblemDetails`. Add a new rule here, not in the service.
- `Infrastructure/Services/LeagueService` and `InviteService` (both `AddScoped`, both take `AppDbContext`) own every league/membership/invite operation; `Api/Endpoints/LeagueEndpoints.cs` and `InviteEndpoints.cs` are thin — resolve `HttpContext.GetMembership()`, call one service method, catch `LeagueRuleViolation` and return `.ToProblem()`. `MeEndpoints.ToResponse` calls `LeagueService.ListMineAsync` for `MeResponse.Leagues` — do not duplicate that query.
- **Effective per-league display name**: always go through `Domain/Leagues/MemberNameProjection` — `.Selector` is an `Expression<Func<Membership, string>>` for a LINQ `Select` (EF pushes `DisplayNameOverride ?? User.DisplayName` into SQL), `.Effective(membership)` is the same rule for an already-loaded entity (needs `.Include(m => m.User)`). Every DTO that carries a member name (`MemberRow` today; P1-03's other surfaces, the dashboard, the leaderboard later) must use one of these two, never `?? ` by hand, or the two will drift.
- Uniqueness on `PUT /api/leagues/{leagueId}/members/me/display-name` is checked case-insensitively against **active** members only (`RemovedUtc == null`) via `.ToUpper()` on both sides inside the EF query (not `StringComparison.OrdinalIgnoreCase`, which does not reliably translate to SQL) — a removed member's old name is free for anyone (see the `DisplayNameConflictTests` "removed member" case). Response is the caller's own updated `MemberRow` (D-039), not `LeagueDetail`.
- **Invite accept reactivates, never duplicates**: `Memberships` has a unique index on `(LeagueId, UserId)`, so a former member accepting a new invite has their existing row's `RemovedUtc` cleared and `JoinedUtc`/`JoinedWeek`/`Role` reset, rather than a second row (D-037). `InviteService.ResolveAsync` picks one `InviteState` when several apply: Revoked > Expired > AlreadyMember > Full (D-038). Invite codes are 8 chars from an unambiguous alphabet (no `0/O/1/l/I`) via `InviteCodeGenerator.Generate()` (`RandomNumberGenerator`); `InviteResponse.Url` is `{App:PublicOrigin}/join/{code}`, falling back to the request's own scheme+host when that config key is unset.
- **Seeding a league in a test**: `TestUsers.CreateLeagueScenarioAsync(factory)` (already existed from P0-03) gives you a league with a commissioner and a member plus a stranger with no membership — use it for anything role/auth shaped. ## Domain events (from P2-03)
- Events are records in the feature folder that owns them (`Domain/Seasons/Events/GameWentFinal`, `GameScheduleChanged`), implementing `Domain/Events/IDomainEvent`. **Define a new one**: `public sealed record WeekLocked(...) : IDomainEvent { public DateTime OccurredUtc { get; init; } }`. `OccurredUtc` is an `init` property, not a constructor parameter — the Domain project has no clock, so the raising service sets it (D-046). Write handlers idempotently: the event is dispatched after the save, so a crash in between loses it, and the nightly recompute is the real backstop.

- **`Domain/GameSets/WeekGameSetLockGuard` is the one lock test** (D-110): `IsFrozen(set, nowUtc)` = `LockedUtc != null || nowUtc >= LockAtUtc`, plus `IsNotFrozen(nowUtc)` as an `Expression` for queries. `GameSetService` (generate, manual add/remove, week rules), `PointRuleService` (override, and the re-resolve sweep) and `PickService` all go through it, so **configuration is refused from the lock instant, before the job has run**. Anything new that mutates a week must use it rather than reading `LockedUtc` by hand. `PointRuleService` took a `TimeProvider` for this. Exception: `ScheduleChangeHandler` still branches on `LockedUtc` alone, deliberately (P5-02 owns the locked-and-disrupted game).
- `PointValueRecalculator.LoadLatestSpreadsAsync(db, gameIds, ct)` is the shared "newest `GameLines.Spread` per game" query; the lock job needs the value itself for `SpreadAtLock`, so it does not go through `RecalculateAsync`.
- **Driving the lock in a test**: `ActivatorUtilities.CreateInstance<LockWeekJob>(scope.ServiceProvider)` off a real app container, then `RunAsync(new OneShotOccurrence(setId.ToString("N"), lockAtUtc))` — see `LockWeekJobTests`/`PostLockMutationTests`. Two traps in the shared database: (1) `GetDueAsync` is **global**, so a scheduler tick locks every other league's due week too — `LockWeekJobTests` ticks against a bespoke league holding only fixture game 700016 (Saturday 00:30 ET, the earliest kickoff in the week) so the pass has exactly one week to do; (2) a tick of the app's own `SchedulerTick` also fires the cron jobs, and a dozen heartbeat rows dated in the fixture season push real rows out of `GET /api/admin/data-status`'s newest-50 list and fail `AdminDataStatusTests`. Use `SchedulerHarness` with only the job under test.
- `HealthEndpointTests` asserts the first applied migration is the initial schema and that nothing is pending, not a migration count — P4-01 and P7-01 both had to relax that assertion in the same week. Adding a migration should not need that test touched again.
- **Two branches each adding a migration collide in a way the merge does not flag**: the merged `AppDbContextModelSnapshot.cs` is correct, but the *newest* migration's `.Designer.cs` still holds only its own branch's model, and EF's `PendingModelChangesWarning` then fails every database test with "the model has pending changes". The fix is to delete your migration, restore the snapshot from `main`, and re-add it so it is generated on top of theirs (P4-01 did exactly this with `Phase4_01_GameSetGameAddedUtc`). `dotnet ef migrations add ZzTempVerify` producing an empty `Up`/`Down` is the check that the snapshot and the model agree — remember `migrations remove` afterwards, and note it rewinds the snapshot to the previous migration's Designer model, so re-check the snapshot after using it.
- **P4-04's handlers**: `Infrastructure/Services/PickGameChangeHandlers.cs` has `GameAddedPickHandler : IDomainEventHandler<GameAddedToSet>` and `GameRemovedPickHandler : IDomainEventHandler<GameRemovedFromSet>`, both registered in `AddInfrastructure` right after `ScheduleChangeHandler`'s line. Neither re-derives status math — they just decide *who* to recompute and *who* to flag, then call `PickService.RecomputeWeekStatusesAsync`. `GameAddedPickHandler` reads every membership that already has a `WeekSubmissions` row for the set and passes that same list as `markUnseenGameChangesFor`, so an existing `Submitted`/`InProgress` member is recomputed and flagged (a brand-new `NotStarted` member gets neither, matching "a row is created only when the member has something to say"). `GameRemovedPickHandler` instead flags only the memberships with a `Picks` row on the removed `WeekGameSetGameId` — everyone else with an existing submission row still gets recomputed (their `TotalCount` changed) but not flagged, and the `Picks` row itself is never touched (D-008). Both are no-ops on a locked week purely because `RecomputeWeekStatusesAsync`/`RecomputeCoreAsync` already refuse one (D-046's "written after save" applies here too: a crash between save and dispatch just means the nightly recompute, if one ever ships, is the backstop — today there is none, so a lost dispatch leaves the stored row stale until the member's next pick/submit recomputes it themselves via `ApplyStatusAsync`).
- **Why the stored row matters, not just `GetMyPicksAsync`'s live computation**: `GetMyPicksAsync`/`GetStatusRosterAsync` both recompute `SubmissionStatusCalculator.Calculate` on every read (pre-lock), so they would show the right answer even with no handler at all. `LeagueService.ListMineAsync`/`GetMembersAsync` (`GET /api/leagues`, P1-01) read `WeekSubmissions.Status` directly with no recompute — that is the one surface a missing or broken handler actually breaks, and the sharpest thing a P4-04 test can assert against.
- **Ordering relative to P7-03**: P7-03's notification handlers for the same two events compute their own recipient list from `Status == Submitted OR SubmittedUtc != null` read at dispatch time, independent of anything P4-04's handlers write, so registration order between the two never matters — confirmed by keeping both handler pairs registered as separate `AddDomainEventHandler` lines rather than folding one into the other.

## Scoring (from P5-01)
- **`Domain/Scoring/WeekScorer.Score(WeekScoringRequest)`** is the whole of Feature 06's arithmetic: pure, no clock, no entities, no week number. In: `Games` (every `WeekGameSetGames` row of the set, removed and voided included), `Members` (every `WeekSubmissions` row of the set, whatever its status), `Picks`. Out: `WeekScoreResult(Members: MemberWeekScore(MembershipId, Points, CorrectCount, ActiveGameCount)[], IsWeekComplete, NeedsReviewGameSetGameIds)`. It filters both lists itself (D-128) — active = `!IsRemoved && !IsVoided`, scored = a submission row reading `Locked` or `Incomplete` — so **do not pre-filter in the caller's query**. Winner is `WinnerResolver.Resolve` and nothing else (D-098). `NeedsReview` is the active rows that are Final with no determinable winner; those also hold `IsWeekComplete` false. An all-voided week is Complete (D-133).
- **`Infrastructure/Services/ScoringService`** (scoped) is the only thing that writes `WeekResults`. `RescoreWeekAsync(weekGameSetId, ct)` → full recompute, upsert (PK `MembershipId`+`WeekGameSetId`), stamp `WeekGameSets.IsComplete`, returns the `WeekScoreResult` (or null when the set does not exist or has not locked — **an unlocked week is never scored**). `RescoreGameAsync(gameId, ct)` → every locked set with an active row for that game, across leagues, then `RescoreWeekAsync` each; that is what makes a post-midnight finish score against the week it kicked off in, since the league's own sets are asked and the provider's week number is never read. Stale result rows whose membership the scorer no longer produces are deleted (D-131); `ComputedUtc` is stamped on every recompute, including a no-op one (D-130).
- **The snapshot seam for P5-03**: `Infrastructure/Scoring/IStandingsSnapshotWriter.WriteSnapshotAsync(Guid leagueId, int throughWeek, CancellationToken ct)`. `ScoringService` calls it **exactly once per week, on the transition from not-complete to complete, after its own `SaveChangesAsync`** — so an implementation reads `WeekResults` that already agree with the closed week, and a later rescore of an already-closed week writes nothing (D-129, D-007). `AddInfrastructure` has `services.TryAddScoped<IStandingsSnapshotWriter, NoOpStandingsSnapshotWriter>()`: **P5-03 registers its real writer on an earlier line in the same method** and the `TryAdd` then no-ops. Implementations must be idempotent — the nightly sweep can close the same week again after a rollback.
- **The events P5-02 raises**: `Domain/Scoring/Events/ResultOverridden(LeagueId, Week, WeekGameSetId, GameSetGameId, GameId, WinnerTeamId, ActorMembershipId)` and `GameVoided(LeagueId, Week, WeekGameSetId, GameSetGameId, GameId, Reason, ActorMembershipId)`, both already defined and already subscribed (`ResultOverriddenScoringHandler`, `GameVoidedScoringHandler` → `RescoreWeekAsync`). They are **league-scoped** and name the set row directly (D-132), unlike `GameWentFinal`: write the `WeekGameSetGames` column and the `AuditLog` row, `SaveChangesAsync`, then raise — the P2-03 order. P5-02 adds no scoring code; setting `ResultOverrideWinnerTeamId`/`IsVoided` and raising the event is the whole integration.
- **`Infrastructure/Jobs/NightlyRescoreJob`** (`30 4 * * *` Eastern, registered with `AddScheduledJob`): every locked non-complete week, plus any set whose `IsComplete` disagrees with its own `WeekResults.IsWeekComplete` (D-134). Failures are isolated per week and the change tracker is cleared between them. This is the backstop for D-046's "a handler that throws is logged and skipped".
- **How the tests drive finals**: `tests/NcaafPickEm.Api.Tests.Infrastructure.ScoredWeekScenario.CreateAsync(factory)` seeds a locked week 7 over the 13 Saturday-Eastern FBS fixture games with three settled members (home-picker, away-picker, a partial `Incomplete` one) plus one membership with **no** submission row, frozen point values of 10 except the Iowa State/Kansas tie (15) and the San José State/Hawai'i late game (35). Rows are seeded directly rather than through `GameSetService`/`PickService`/`LockWeekJob` — scoring only reads what they leave behind. Then `FixtureSnapshotState.Set(n)` + `SaturdayPoller.PollOnceAsync` per snapshot drives the real `GameWentFinal` pipeline. **Use a throwaway `SqlTestDatabase`**, never the shared fixture database: advancing snapshots writes real scores onto shared `Games` rows. `RecordingStandingsSnapshotWriter` swaps in via `ApiFactory(..., configureServices: s => { s.RemoveAll<IStandingsSnapshotWriter>(); s.AddSingleton<IStandingsSnapshotWriter>(fake); })`. Expected totals across the walk are 10 → 50 → 90/20/10 → +35 for the late game → +15 to the away-picker once the tie is overridden.

## Leaderboard (from P5-03)
- `Domain/Leaderboard/StandingsCalculator` is the whole of `04` section 8: pure, static, no clock, no entities. `SeasonRows(activeMembers, results, snapshots, viewerMembershipId)`, `WeekRows(week, members, results, isComplete, viewerMembershipId)`, `GridCells(games, membersWithSubmission, picks)` and `ComputeSnapshot(members, results, throughWeek)`. In: `StandingsMember(MembershipId, DisplayName, IsFormer, JoinedWeek)`, `StandingsWeekResult(MembershipId, Week, Points, CorrectCount, ActiveGameCount, IsWeekComplete)`, `StandingsSnapshot(ThroughWeek, MembershipId, Rank, TotalPoints)`, `GridGame(GameSetGameId, IsVoided, WinnerTeamId)`, `GridPick(MembershipId, GameSetGameId, TeamId)`. Out: the `Shared/Contracts/Leaderboard` rows themselves (`SeasonRow`, `WeekRow`, `GridCell`) - the one place `Domain` returns a contract record rather than a twin, D-139 - plus `StandingsSnapshotRow` for the writer. **`GridGame.WinnerTeamId` is the caller's answer from `WinnerResolver` (D-098)**; the calculator never re-derives a winner, and it ignores any pick or result belonging to a membership the caller did not list.
- Rules worth knowing before you change one: ordering is score desc, then display name (`OrdinalIgnoreCase`), then `MembershipId`; ranking is competition "1224"; season totals and weekly wins skip weeks before a member's `JoinedWeek`; a week counts for `WeeklyWins` only when **every** result row for it says `IsWeekComplete`, and the week's max is taken over all rows including former members' (D-141); `Trend` compares the two highest `ThroughWeek` values present in the snapshots and is `None` for anyone missing from either.
- `Infrastructure/Services/LeaderboardService` (scoped; `AppDbContext` + `GameSetService`) owns `GET /api/leagues/{leagueId}/leaderboard`, `.../weeks/{week}/leaderboard` and `.../weeks/{week}/grid`. The season read is three queries (active memberships, the league's `WeekResults` joined through `WeekGameSets` for the week number, snapshots) and `ThroughWeek` is the max week with any result row, null before the first scored week. The week read runs `WeekRangeGuard` (404 out of range), returns an empty `WeekLeaderboard` when the week has no set, and takes its members from *the result rows* so former members keep the weeks they played. The grid throws `PickRuleViolation(PicksNotVisible)` → 403 until `LockedUtc != null` (same code and title as `GET .../picks`), takes its games from `GameSetService.GetWeekGameSetAsync` (voided included, `WinnerTeamId` already derived by `GameSetGameDtoMapper`), and its columns from the `WeekSubmissions` rows, ordered by effective name - use `MemberNameProjection` for every name, never `??` by hand.
- **"Who was in the league at lock" is a `WeekSubmissions` row with `Status` in (`Locked`, `Incomplete`)**, never merely "has a row" (D-135, D-142). `PickService` writes a row the moment a member first touches a week and D-111 leaves it behind when the locker drops the membership, so the status clause is what keeps a member who picked and then left *before* lock out of the grid, the all-picks view and the dashboard, while still keeping one removed *since* lock in (flagged `IsFormer`). All three surfaces (`LeaderboardService.GetGridAsync`, `PickService.GetAllPicksAsync`, `DashboardService`) now share it; anything new that answers the same question must too.
- `Infrastructure/Scoring/StandingsSnapshotWriter` is the real `IStandingsSnapshotWriter` behind P5-01's seam: recompute `ComputeSnapshot` over active memberships and the results through that week, upsert the `(LeagueId, ThroughWeek)` rows, delete rows for memberships no longer active, `SaveChangesAsync`. It runs in `ScoringService`'s own scope and `AppDbContext` and never clears the change tracker. Registered with `AddScoped` **above** P5-01's `TryAddScoped<IStandingsSnapshotWriter, NoOpStandingsSnapshotWriter>()` in `AddInfrastructure`; that ordering is what makes the real writer win, and `StandingsSnapshotWriterTests` asserts it by resolving the interface from the app container.
- `GET /api/leagues/{leagueId}/weeks` now reports `HasGameSet` only when the week holds at least one active `WeekGameSetGames` row (D-140) - a `WeekGameSets` row alone is created by merely touching a week, and P5-04's prev/next reads this flag.
- **Seeding a leaderboard in a test**: `WeekResults` rows go in directly (`LeaderboardEndpointsTests` does; `ScoredWeekScenario` + `ScoringService` is the other way in). Two traps: the `Games` rows are shared by every league in the run's database and other suites advance the fixture score snapshots, so a test that needs a game with **no** winner must set that row's `Status`/scores itself and restore them in a `finally`; and a per-league result belongs on the `WeekGameSetGames` row (`ResultOverrideWinnerTeamId`, `IsVoided`), never on the shared `Games` row.
## Corrections (from P5-02)
- **`Infrastructure/Services/CorrectionService`** (scoped) is the whole of Feature 06's corrections API: `OverrideResultAsync(caller, week, gameId, winnerTeamId, reason, ct)`, `VoidGameAsync(caller, week, gameId, reason, ct)`, `GetAuditAsync(leagueId, ct)`. Both mutations load the row through one private `LoadLockedRowAsync` (404 `GameNotFound` if the row does not exist or was manually removed, 409 `NotLocked` via `WeekGameSetLockGuard.IsFrozen` if the week has not locked yet), then write the `WeekGameSetGames` column, an `AuditLog` row, `SaveChangesAsync`, and raise `ResultOverridden`/`GameVoided` — P5-01's `ResultOverriddenScoringHandler`/`GameVoidedScoringHandler` (already registered) do the actual rescoring. **This service adds no scoring logic**: it never calls `ScoringService` directly. The returned `GameSetGameDto` comes from re-calling `GameSetService.GetWeekGameSetAsync` after the save+dispatch and picking the matching row out of it, rather than building the DTO by hand a second time.
- **Rule details**: overriding a voided row is refused (409 `AlreadyVoided`) — a void is one-way. `WinnerTeamId` must be the game's home or away team (400 `TeamNotInGame`) — checked against the loaded `Game`, not against `WinnerResolver`. A second, identical override is **not** a no-op (D-143): it writes a fresh audit row and re-raises the event every time, on the reasoning that a repeated commissioner call is not this service's call to silently swallow, and the rescore it triggers is deterministic anyway. Voiding an already-voided row stays a 409 (`AlreadyVoided`) with no re-audit path, since there is nothing to confirm a second time.
- **`Domain/Scoring/CorrectionRuleViolation`** (`NotLocked`/`AlreadyVoided` → 409, `TeamNotInGame`/anything else → 400, `GameNotFound` → 404) is separate from `GameSetRuleViolation` (D-144) — `GameSetRuleViolationCode.Locked` means the opposite thing (week *is* locked, mutation refused) from what a correction needs to say. `CorrectionEndpoints` still catches `GameSetRuleViolation` too, because `WeekRangeGuard` (shared with every week-scoped route) throws that type for `WeekOutOfRange`.
- **Audit summaries**: `GetAuditAsync` builds `AuditEntry.Summary` per `AuditAction`, covering every action the codebase writes today, not just the two P5-02 owns (D-145) — `ResultOverride`/`GameVoided` (mine), `GameManuallyAdded`/`GameManuallyRemoved` (P3-03), `MemberRemoved`/`RolePromoted`/`RoleDemoted`/`RoleTransferred` (P1-01), `ManualRefresh` (P2-04). Game-shaped actions resolve team names from a `gameId` property in `Details` (P5-02 added `gameId` to `ResultOverride`/`GameVoided`'s own `Details`, D-146, matching the shape `GameManuallyAdded`/`Removed` already used); member-shaped actions resolve a name from `TargetId` (already the target membership id on every one of those four actions) via `MemberNameProjection`. Both are one batched query each, not N+1. An action nobody recognizes falls back to `Action.ToString()` rather than throwing. `ActorName` is `MemberNameProjection.Effective` off the included `ActorMembership.User`, or `"System"` if that navigation is somehow null (never happens today; defensive only).
- **The needs-review → one-tap-void route for P5-05**: `NeedsVoidReviewItem` already carried `WeekGameSetId`/`GameSetGameId`/`LeagueId`/`Week` (P3-04). `Shared/Contracts/Admin/NeedsReviewGameDto` — the DTO `GET /api/admin/data-status` actually serializes — was missing `WeekGameSetId`/`GameSetGameId`; both are now additive optional fields (D-147), populated on both branches of `AdminEndpoints.GetDataStatusAsync`'s combined `NeedsReview` list. P5-05's UI can `POST /api/leagues/{LeagueId}/weeks/{Week}/gameset/games/{GameId}/void` straight off a `NeedsReviewGameDto` row with no second lookup. `GameNeedsVoidReviewHandler : IDomainEventHandler<GameNeedsVoidReview>` (registered) does nothing but log at Information — it exists only to quiet the dispatcher's "no handler" debug line; the actual surfacing mechanism is still `GameSetService.ListNeedsVoidReviewAsync` feeding the data-status page, unchanged from P3-04.
- **Endpoints**: `Api/Endpoints/CorrectionEndpoints.cs` — `POST /api/leagues/{leagueId}/weeks/{week}/gameset/games/{gameId}/override-result` and `/void` (`RequireLeagueCommissioner()`, `ValidationFilter<T>` for `Reason` 1..200), `GET /api/leagues/{leagueId}/audit` (`RequireLeagueMember()`, newest-first, capped at `CorrectionService.AuditCap` = 200).
- **Testing**: `OverrideTests`/`VoidTests` each get their own throwaway `SqlTestDatabase` + `ApiFactory` (like `ScoringServiceTests`), advance `FixtureSnapshotState` to `MaxSnapshot` and run `SaturdayPoller.PollOnceAsync` once in `InitializeAsync` so every fixture game (including the Iowa State/Kansas tie) is already Final before `ScoredWeekScenario.CreateAsync` seeds a league over them, then drive the real HTTP endpoints rather than raising events by hand. `CorrectionsAuthMatrixTests` cannot use the generic `AuthMatrix.RunAsync` helper for the two `POST` routes (it needs a route that succeeds for a fresh, un-set-up league, and these routes never do) — it seeds its own tiny locked scenario directly (one fixture game, `LockedUtc` set by hand, same pattern as `ScoredWeekScenario`) and runs the 401/404/403/2xx checks by hand against it.

## Dashboard (from P6-01)
- `Domain/Dashboard/InfluenceCalculator.Calculate(InfluenceRequest)` is the whole influence dashboard: pure, no clock, no entities. In: `InfluenceRequest(ViewerMembershipId, Games: InfluenceGame[], MembersActiveAtLock: InfluenceMember[], Picks: InfluencePick[])`. Out: `InfluenceResult(Games, EveryoneAgrees, PointsSoFar, MaxRemaining)` where each entry is `InfluenceGameResult(GameSetGameId, MyTeamId?, MyOutcome, OppositeCount, OppositePicks, NoPick, HomePickers, AwayPickers, SwingPoints, WinnerTeamId?)`. `InfluenceOutcome` (Pending/Won/Lost/NoPick) is in `Shared/Enums`, so `DashboardGameDto` uses the same enum (D-014). - **How P6-02 builds the request.** `ViewerMembershipId` = the caller's membership from the endpoint filter. `Games` = the set's `WeekGameSetGames` where `IsRemoved = 0`, projected with their `Game` (status, scores, kickoff, teams), `ResolvedPointValue` (frozen at lock) and `ResultOverrideWinnerTeamId`/`IsVoided`; pass voided rows in or leave them out, the calculator drops them either way. **`MembersActiveAtLock` = the memberships with a `WeekSubmissions` row for this set whose `Status` is `Locked` or `Incomplete`** (the two the lock job writes — D-135; a bare "has a row" test also names a member who picked and then left *before* lock, because `PickService` creates the row and D-111 leaves it behind) — that single query is what includes a member removed since lock (set `IsFormer` from `Memberships.RemovedUtc != null`) and excludes one who joined after it; the calculator never looks past the list, so getting this query right is the whole rule. `DisplayName` is the league nickname when set, else the global one (`MemberNameProjection`). `Picks` = `Picks` rows joined to those game-set-game ids. Two queries, as the card asks.
- The result is ordered; render it in order. `Games` is the main list, `EveryoneAgrees` the collapsed one, and a game the viewer did not pick stays in `Games` with `HomePickers`/`AwayPickers` filled so the card can show both sides. `MyOutcome` is Won/Lost as soon as a winner exists (override included), never before; a Final tie reads `Pending`.

- **The endpoint (P6-02)**: `Infrastructure/Services/DashboardService.GetAsync(viewer, week, ct)` is `GET /api/leagues/{leagueId}/weeks/{week}/dashboard` (`Api/Endpoints/DashboardEndpoints.cs`, `RequireLeagueMember()`, no `asMember` — any query string at all is 400 `UnsupportedQueryParameter`, since a member only ever sees their own dashboard, D-119).
